# GPAP — artifact guide

Everything in the paper's evaluation section, and how to re-derive it. One script does all of it:

```bash
eval/artifact/reproduce.sh check      # what this machine can do, and what each tier will cost
eval/artifact/reproduce.sh tables     # TIER 1: every table and figure, from the shipped rows
eval/artifact/reproduce.sh setup      # build and fetch everything the GPU tiers need
eval/artifact/reproduce.sh smoke      # TIER 2: 4 cells end to end, compared to the published ones
eval/artifact/reproduce.sh subset     # TIER 3: 66 of the 142 cells, re-measured
eval/artifact/reproduce.sh full       # TIER 4: all 142 cells
```

Each step prints what it is about to do and what it is expected to cost before it starts.

## Tier 1 — every table and figure, on any machine (~1 min, no GPU)

The artifact carries the campaign's per-instance rows. `reproduce.sh tables` regenerates
Tables 1, 2, 3 and 4b, both figures, the publishability gate and the emission audit from them:

```bash
eval/artifact/reproduce.sh tables          # writes under .experiments/artifact/
```

`--out DIR` puts them elsewhere. The default stays inside the repository's own disposable
root, so nothing lands in `/tmp`, where the next reboot is free to take it.

The table generators and the gate are pure JSON readers — **no GPU, no CUDA wheels, not even
numpy** (gated by
`tests/experiments/test_paper_tables.py::test_the_table_generators_import_without_torch_or_numpy`), so they
run under a stock `python3` in the TACAS evaluation VM. Their output is byte-identical to the
paper's tables apart from a date and commit line in each header. Only the two figures need
anything extra (`matplotlib`); without it that step says so and the rest still completes. With
matplotlib 3.10.8 (numpy 2.4.4), `plots/sps_scatter_cmsgen.pdf` (the file the paper includes as
Figure 1) and its `.png` are byte-identical to the paper's; another version draws the same points
with different pixels.

| what it writes | what it is |
|---|---|
| `RESULTS.md` | every table, and the ledger and caveats behind each one |
| `paper_numbers.json` | every number the paper prints, machine-readable |
| `PAPER_NUMBERS.txt` | `paper_numbers.json` against what the submitted PDF prints |
| `VERIFICATION.txt` | the publishability gate: every caveat the paper's text is required to state |
| `emission_audit.txt` | re-derives that no tool was timed while writing samples out |
| `plots/` | both scatter figures, drawn through the tables' own cell classifiers |

The paper typesets its own tables — it drops columns and renames rows to fit an LNCS page — so
nothing can byte-compare them against generated LaTeX. `check_paper_numbers.py` closes that gap
instead: `docs/papers/tacas-27/published_numbers.json` records what the PDF prints and which
generated row each value checks, and the step fails if the two disagree. Shapes may differ;
numbers may not. A value is compared at its own printed precision, a count exactly.

### Claim → table → generator → data

| the paper says | where | generated by | from |
|---|---|---|---|
| 83.4–1,571× CMSGen's throughput | Table 1 | `paper_tables.py --rivals` | `artifact-data/paper/data/rivals_*.json` |
| 2.2–18.7× the GPU samplers at their own targets, ~2 orders at ours | Table 2 | same | same |
| the speedup is rejection cost, not engine speed | Table 3 | same (`prop_rates`) | same rows as Table 1 |
| Barbarik accepts GPAP on all 65 eligible instances, as it does CMSGen | §Sample Uniformity (prose) | same (`--barbarik`) | `artifact-data/paper/data/barbarik/*.jsonl` |
| 93 of 110 instances delivered all 50,000 samples, CMSGen 44 | §eval text | same (`--out-json`) | same rows as Table 1 |
| every emitted sample is a solution | `VERIFICATION.txt` | `verify_artifact.py` | the `sound_check` / `sim_check` of every row |
| every number above matches the PDF | `PAPER_NUMBERS.txt` | `check_paper_numbers.py` | `paper_numbers.json` + the published transcription |

The exclusion rules live in exactly one place, `eval/artifact/paper_tables.py`; every other
consumer (figures, slides, the gate) imports them, so a table and a figure cannot disagree about
which cells count. `docs/papers/tacas-27/README.md` states each rule and what it costs us.

## Tier 2–4 — re-measure on a GPU

```bash
eval/artifact/reproduce.sh setup            # libgpap, abc, patched CMSGen and Recurrent, the pinned rivals
eval/artifact/reproduce.sh smoke            # 4 cells: does this machine reproduce the pipeline?
eval/artifact/reproduce.sh subset           # the reviewer tier
eval/artifact/reproduce.sh full             # every cell of the published campaign
```

Every GPU tier ends by regenerating the tables **over its own fresh rows** and then running
`compare_campaign.py` against the published ones.

### What is asked of a reproduction, and what is not

A reviewer's GPU is not ours, and a sampling rate is a property of the card: the same engine
measures 1.82× on an A100 and 0.84× on an L4 against one RTX 4080
(`docs/findings/CROSS_GPU_FINDINGS.md`). Asking for our geomeans back would test the hardware.
So the comparator asserts what must hold on **any** machine, and reports the rest:

| tier | checked how | a failure means |
|---|---|---|
| **the same formula per cell** | `n_vars`, `n_clauses`, `support`, encoder, `pin_check_ok` must match exactly | the two runs did not measure the same thing — usually a different `abc` build |
| **soundness, on its own** | no emitted model may falsify a clause; every kept sample must replay through the original netlist | a real bug, and the paper's central claim |
| **the same verdicts** | which tool won each cell, and how each cell was classified | the conclusion did not survive the hardware |
| *rates* | printed as this card's speed factor against ours | nothing — it is evidence about the machine |

Exit status is non-zero only for the first two.

### Hardware

**24 GB of VRAM reproduces the published run as recorded.** This is not a guess: all 92 pinned
Recurrent-CircuitSAT rungs sit at the reference L4's memory ceiling — the campaign recorded an
OOM one rung above each. On a smaller card those cells walk down a rung, which the rows record
(`grant_source`) and the comparator counts and warns about, **because a rival handed a smaller
batch than the paper gave it makes our ratio look better**. The run still completes.

The opposite direction is handled by `--vram-cap`, on by default. Our own batch is memory-bound
on 63 of the campaign's 141 rows, so an uncapped 80 GB card would hand GPAP more parallelism
while the rival stays pinned to the recorded batch — again in our favour. The default
`--vram-cap l4` holds the engine's memory budget to the 17,280 MiB the L4 run had; it is a
ceiling, so it is inert on smaller cards. `--vram-cap none` measures the card as it is.

Software: an NVIDIA driver, cmake, a C++17 compiler, Python ≥ 3.10, and the Python packages in
`eval/artifact/requirements-artifact.txt`, which fixes the three that can move a number — torch
(every row records its build), the triton that compiles the kernels, and the SAT solver that
adjudicates the `unsat` screen. **Into a virtualenv**, whose `python` every step below then uses:

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r eval/artifact/requirements-artifact.txt && pip install -e .
pytest tests -m "not gpu and not slow"  # optional: the shipped tree's own suite, ~10 s
```

If you would rather not activate it, pass the interpreter explicitly:
`PYTHON=/path/to/python eval/artifact/reproduce.sh …`.

Building the engine needs **no CUDA toolkit installation and never invokes nvcc**:
`scripts/build_core.sh` compiles the kernels through triton and links against `libcuda`, the
driver library. (torch's wheels do pull CUDA runtime libraries as Python packages, one of them
named `cuda-toolkit` — that is torch's own dependency, and nothing in this build calls it.)
There is no CPU execution path: the engine needs a GPU. `reproduce.sh tables` needs none of this:
a stock `python3` runs it.

### What each tier costs

Derived from the published rows themselves — `eval/artifact/estimate_wall.py` prints the table
below for whatever card and settings you ask about, and `reproduce.sh check` runs it for you.

| tier | cells | reference card | what it covers |
|---|---|---|---|
| `tables` | — | ~1 min, CPU only | every published table and figure |
| `smoke` | 4 | ~3 min | one cell per stage, everything else exactly as the real tiers run it |
| `subset` | 66 | ~2.6 h (measured 2 h 50 on a rented L4) | all 22 ISCAS-85 cells and 22 of the 30 sequential instances, T=25 |
| `full` | 142 | ~12.3 h | every cell, T=25 and T=50 |
| `full --remeasure-failures` | 142 | ~22.6 h | the same, re-deriving every recorded rival failure |

What has been run end to end, and against which reference:

- `tables`, from this package, in an offline Ubuntu 24.04 container with only the stock
  `python3` (no GPU, no numpy, no network): the manifest verified, all 163 published values
  reproduced, the gate and the audit passed (2026-10-13, against the 2026-10-12 rows).
- `setup` then `smoke`, from this package, in a fresh virtualenv built from
  `requirements-artifact.txt` on an RTX 4080 Laptop GPU (12 GB): every tool built from its pinned
  source, 4/4 cells with the same formula, sound samples and the same verdicts (2026-10-13,
  against the 2026-10-12 rows; DEMOTIC's two rungs walked down on the smaller card, as stated).
- `subset`, from this package, on a rented L4 (`docs/findings/ARTIFACT_FINDINGS.md` §5b):
  66/66 against CMSGen and 58/58 of the cells whose rival side was measured rather than pinned
  reach the same verdict; every count in Tables 1-3 equals the published rows restricted to the
  same cells, and every ratio is within 5.5% (2026-10-14, against the 2026-10-12 rows). The same
  tier against the earlier 2026-09-04 rows is §5.

The estimate is the recorded per-cell walls plus a measured overhead the rows do not carry
(start-up, the ABC pass and its equivalence check, the soundness replay). It assumes the batch
search is not repeated — see below. Both terms move with the machine: the measured part with the
GPU (`--scale`) and the overhead with the host CPU (`--cpu-scale`), since the ABC pass and the
replay are CPU-bound.

**The reviewer tier's cell set is chosen by the clock, not by us**: a sequential instance is kept
when both its T=25 tasks together cost ten minutes or less on the reference card. The rule,
the selection and the per-instance walls behind it are in `eval/artifact/subset.json`; a
hand-picked list could select for cells we win, and this cannot. The subset's own reference
numbers are what the comparison uses — not the paper's geomeans, which are over all 142 cells.

### Two shortcuts, both stated in every row

**The batch grant is pinned, not searched again.** The protocol grants each rival the largest
batch it runs to completion, walking a ladder down from 30,000,000; deriving that costs many
runs per cell. `eval/rivals/grants/l4_protocol_20260904.json` records what each cell was
granted, and Recurrent's settled `start_point`, so a reproduction pays neither. A pinned rung
this card cannot finish on is walked down from, and the row says which happened. To re-derive
everything from scratch: `--grants none`.

**Recorded rival failures are pinned by default — and the paper's own campaign pinned them
too.** 28 cells are recorded as "the rival did not initialize inside its 1,200 s budget", measured
on the L4 on 2026-09-04; re-deriving them costs that budget each — 10 of the 22 hours of a full
re-measurement — to produce rows that say "no measurement". The 2026-10-12 campaign the paper
reports carried them over from the grants file rather than re-measuring them, and so does this
artifact: such a row is marked `not_remeasured`, `VERIFICATION.txt` names it, and the comparator
refuses it as evidence in either direction. **This can only be unfair to the rival** — a faster
card might initialize where the L4 could not. `reproduce.sh full --remeasure-failures` re-derives
them.

### Known deviations and issues

- `b19` at T=25 under Recurrent's own pins is a GPAP encoder error: `abc` itself crashes on it
  (`aigDup.c:602`). It is one of the 142 cells and is reported as a refusal, never as a zero.
- The uniformity rows (§Sample Uniformity) come from a separate run on a different card, an RTX
  4080, as the paper states: a Barbarik verdict is a property of the sampler, not of the GPU.
  `tables` regenerates the verdict counts from the shipped rows; re-running Barbarik itself needs
  barbarik and SPUR, which are not part of `setup`.
- The GPU rivals are PyTorch programs run as subprocesses. `setup` applies a
  function-preserving Python ≥ 3.13 shim to them (they `exec` generated code and PEP 667 breaks
  it); it is verified bit-identical on 3.12 and changes no rival behaviour.
- Colab and similar rented VMs reclaim the machine after about an hour. Every tier is resumable
  — re-running the same step skips finished cells — and `eval/colab/colab_supervisor.py` drives
  that automatically.

## Reusing the engine

The engine is a library, not a script: `libgpap` with a C ABI (`cpp/include/gpap/gpap.h`), a
header-only C++ wrapper (`gpap.hpp`, with `examples/`), and a Python face (`gpap.engine`).
`docs/ENGINE.md` is the design, `docs/PYTHON_API.md` the supported surface, `cpp/README.md` the
C and C++ entry points. `docs/EVAL_RUNBOOK.md` is the protocol and how to run a campaign of your
own; `docs/BENCHMARKING.md` is how to measure on this class of hardware without fooling yourself.
