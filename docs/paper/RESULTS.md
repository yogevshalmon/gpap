Columns add up: `inst` = `n` + CMSGen=0 + GPAP=0 + excluded. `n` is the number of instances the geomean stands on; `CMSGen=0` / `GPAP=0` are the one-sided zeros (an outright win / an outright loss, no finite ratio); `excluded` is every other cell without a ratio — the instance screens (a vacuous pin, a free support, a tiny solution space, a cell proved UNSAT at this depth), a cell neither sampler reached, a cell GPAP's encoder refused — itemised by name under the table. **Two rate columns, and each charges BOTH sides the same way.** `GPAP/CMSGen` is steady state over steady state: GPAP's winning-config sampling rate over CMSGen's samples per SAMPLING wall (its own `--statsevery` clock, which starts after it has read the CNF). `e2e` is end-to-end over end-to-end: GPAP's `wall_total` (parse + engine construction + ELS + warmup + entailed-clause MINING + the timed run) over CMSGen's whole subprocess wall. `pre%` is the median share of GPAP's end-to-end wall that preparation takes. Earlier revisions scored GPAP's steady state against CMSGen's subprocess wall, which charged one side for getting ready and not the other. Preparation is a real cost at these `n_time` values and does not amortise away until the run is much longer — quote `e2e` for a delivered-samples claim and the steady-state column only for the large-n regime, saying which. The two protocols are DIFFERENT TASKS and must never be pooled: 'their pins' rows pin the 1–5 outputs the rival's own table names (rejection-easy by construction — measured p_accept 0.0029–0.98, 3 cell(s) bounded below 8.1e-08–2.3e-05 where no hit was observed, printed per row), while miter/rare rows pin ALL outputs to a rare reachable pattern (p_accept 3.7e-08–0.5, 17 cell(s) bounded below 4.3e-08–1.1e-05 where no hit was observed). Recurrent-CircuitSAT is scored on its own depth-POOLED unique count — solutions satisfying the target at ANY unroll depth start_point..T, a superset of the fixed-depth task every other row measures (the fixed-depth-only count is recorded per row as `unique_at_T`). **The batch a rival is handed is its score**: measured, both are near-proportional to it over the whole range the card will run (DEMOTIC 564x from 1k to 1M), so it is the same knob `K` is for us. Each rival is therefore granted the LARGEST rung of that ladder it can run to completion: the ladder is walked DOWN from the top and a rung is rejected only on feasibility — out of memory, refused by the driver, or not finished inside the wall budget — never on how fast it was, so exactly ONE configuration is measured per instance. It is a share-of-the-machine rule, not a search for the rival's fastest rung: unique/s stops tracking the batch once the model saturates the card, so a smaller rung CAN score higher, and because the walk stops at the first rung that completes the rival's per-rung optimum is neither sought nor reported — a cell where a shorter earlier budget had measured a smaller rung faster is disclosed in the campaign notes (RIVAL_FAIRNESS_FINDINGS §16c). (Until 2026-09-04 the walk started at our VRAM model's rung, which is calibrated at num_steps=10 while we run 1 and so under-granted DEMOTIC 1.5-3.9x on 4 of 11 ISCAS-85 cells, and a timeout was recorded AS the rival's result.) The first run of every process is discarded before anything is measured, because a cold CUDA context costs the session's first instance ~3.3x. Every rival is handed the SAME circuit file GPAP encodes from — the sequential-ABC-simplified netlist (`variant: abc` on every row). The raw-netlist axis was not run in this campaign, and GPAP's post-unroll ABC pass has no sequential equivalent the rival could be given; that residual is a property of GPAP's encoder and is stated, not corrected. The rungs tried are recorded per row as `batch_sweep`, the resolved budget as `vram_budget_bytes`. Their own defaults cannot serve as the rule — all three argparse defaults are `--batch_size 10` and their demo scripts are per-instance one-liners spanning 1,000 to 1,000,000 on comparably tiny circuits, which on our instances would hand them a small fraction of their achievable throughput and inflate the ratios below by the same factor. **Their `--num_steps` and `--lr` are theirs, not ours**: the batch is a share of the machine and must be granted, but the gradient-step count and the learning rate are tool settings with author-chosen values, so each rival runs at the ones its OWN artifacts specify — `num_steps` 1 and `lr` 15 for both (their `script/run_sampler_*.sh`). Their PAPERS state other values — DEMOTIC 10 iterations at `lr` 15, Recurrent 5 iterations at `lr` 50 — and the campaign runs the SHIPPED script configuration, one per tool, which is also the better of the two for each tool on this card at the depth measured (both saturate their batch on the first step; the paper values, singly and as the paired setting, are measured beside it in `rivals_steps_calibration*.json` so the text can say what they would have given the tool). Recorded per row as `steps`/`steps_source` and `lr`/`lr_source`. Nothing is swept, since a swept-and-best-of setting invites "why stop there?". Recurrent's `start_point` initialization search is given its own 1,200 s budget per instance, which BOUNDS the search and is in no published rate (this table carries no end-to-end column, see below); a cell that does not initialize inside the budget is reported with that budget named, never as a zero. Rows recorded on or before 2026-08-26 pinned 10 for both, which taxes DEMOTIC 2.6x and Recurrent 8.5x (both saturate their batch on the first step) and is why the DEMOTIC and Recurrent rows here are far below their previously recorded values. Rival rows recorded before 2026-08-25 used a fixed 5 GiB budget and are not comparable to rows from the current harness. Constraint alignment is VERIFIED per row: miter mode asserts p(MITER=1) equals the instance's p_accept; native mode asserts bit-identical acceptance words between their index table on the original file and our reordered pins (`pin_check_ok`). **No tool is timed while delivering its solutions**: CMSGen runs under the patch's `--nowrite`, DEMOTIC counts and dedups its solutions after its own timer stops, and our timed run gathers no model row to the host (`collect=False`; the rival arm keeps EVERY delivered row as GPU-projected support bits and deduplicates them exactly, off the clock, the same quantity both rivals report — the dedup runs after the sampler returns and is timed as `distinct_s`, and the projection wall that gathered the rows is subtracted from the steady-state AND the end-to-end rate, so measuring distinctness cannot pay for itself out of the number it measures) — re-derived from the pinned sources by `eval/rivals/check_emission_symmetry.py`. The one exception is Recurrent-CircuitSAT, which copies its per-depth candidate assignments to the host inside its timed loop: the share of its `model_runtime` that costs is bounded per row by the audit script (section 4 of its report — quote the campaign's figure, it depends on the card's transfer rate) and left uncorrected so its rate is exactly the one it publishes. Deducting it would RAISE the ratios below, so those rows under-report GPAP rather than flattering it.

**One clock, and `ties`.** This table has NO end-to-end column, by rule (protocol v1.0, RIVAL_FAIRNESS_FINDINGS.md §17): the rivals' metric is unique solutions per second of their own `model_runtime`, which excludes their model build, and GPAP's figure excludes its construction the same way — that is the one comparison the rivals themselves define. An end-to-end ratio across an in-process sampler and a subprocess gradient tool had four definitions in three review rounds (0.8x, 7.6x, 20.9x/132.0x and 11.8x/68.8x on the same rows), and on DEMOTIC's cells both tools finish the real work in under a second, so it measured process start-up; the end-to-end comparison is Table 1's, where both walls are the same kind of thing. `ties` counts cells whose win/loss sign lies inside GPAP's own seed band (the ratio at its slowest and fastest seed straddles 1.0, against a rival that ran once); `wins` excludes them, so wins + ties + losses = the win denominator.

## Table 3 — propagation throughput (the engine, not the sampler)

`impl/s` is Boolean implications per second: GPAP's from the packed-word kernel, CMSGen's from its own `--statsevery` counters. The last three columns factor the sample-rate result exactly — **engine advantage / work per sample = samples/s ratio** — because GPAP discards a conflicted trajectory (rejection sampling) where CMSGen backtracks and keeps the partial work. That identity is ALGEBRAIC, not a validation: defining work-per-sample as the quotient of the two rates makes it true by construction, so it can only fail if an aggregation mixes row sets — which is exactly the per-column-filtering error it is here to catch, and all it should be claimed to catch. ## Table 4b — Barbarik CM_test (the standard certificate)

`eps=0.3 eta=1.8 delta=0.1` — the parameters CMSGen's own authors certify at (FMCAD'21 Table I): 36 rounds x (1 + 1 + 50) = **1,872 samples** for an Accept, per-round accept band **[0.05, 0.95]**. An Accept means *not caught being eta-far* (L1 >= 1.8, i.e. TV >= 0.90) and holds only under Barbarik's non-adversality assumption; a Reject is unconditional. It is not a proof of uniformity — the exact-oracle fuzzing campaign (docs/findings/UNIFORMITY_FINDINGS.md) is the sensitive instrument.
